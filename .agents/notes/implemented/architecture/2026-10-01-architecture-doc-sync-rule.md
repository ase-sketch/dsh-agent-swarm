# 架构文档同步规则：模块边界变更必须同轮回写 ARCHITECTURE.md

## Problem

2026-10-01 代码质量审查发现 `ARCHITECTURE.md` 的模块边界仍只列 5 个源文件与一条依赖链，
而 M4a 之后真实代码已有 12 个源文件（`swarm-registry.ts`、`remote.ts`、`remote-descriptor.ts`、
`client/**` 4 个、`scripts/build-client.mjs` 全部不在文档里）。
问题不在于"漏写一次"：本仓的里程碑收口门禁第 2 条就是"对照 ARCHITECTURE.md 审查模块边界没被突破"，
参照物滞后即门禁失效——文档漂移会静默地把门禁变成形式。

## Decision

1. 补齐 `ARCHITECTURE.md`：模块边界树（12 个源文件 + client 子目录 + 构建脚本 + 文档）、
   依赖方向（拆成 host 半 / client 半）、host-client 双半数据流、构建与交付链。
2. 在该文件末尾新增「维护规则（本文件的自我约束）」段落：模块边界、依赖方向、双半数据流、
   构建链任意一项变化时**必须同轮回写本文件**，并写明门禁失效的实例作为依据。
3. 在双半数据流一节明确"结果权威口径"：工具返回的 XML 是成员状态的唯一权威，面板只是过程可见性。

## Alternatives considered

- **只补内容、不加维护规则**：否决。本次漂移的成因不是疏忽一次，而是缺少"何时必须回写"的触发条件；
  不写规则就会复发（同一个文件、同一个原因，下次换个里程碑）。
- **模块边界改为脚本自动生成（从 import 图导出）**：否决。import 图表达不了"双半数据流""权威口径"
  "挂载层序"这类语义；也会给一个本地插件引入额外的文档工具链。
- **规则下沉到 per-module 的 AGENTS.md**：否决。规则下沉适用于语言/框架专有约束；
  模块边界是全局单一事实来源，拆开会产生互相矛盾的多份边界描述。

## Consequences

- 收益：收口门禁恢复有效参照物；新增模块时有明确的回写义务。
- 代价：结构性改动多一次文档编辑（分钟级）。若不执行，代价是下一次审查重复同一条发现。

## Confirmation

- 即时校验：`ARCHITECTURE.md` 的模块树与 `src/**` + `scripts/**` 的实际文件一一对应（12/12）。
- 持续校验：每次里程碑收口时逐条对照本文件；新增源文件而未回写即视为门禁未通过。
